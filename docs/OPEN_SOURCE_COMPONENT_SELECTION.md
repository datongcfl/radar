# Radar 开源组件选型与治理策略

> 状态：M14 初稿 / 调研中  
> 适用范围：Radar 通用核心、来源适配器、文档解析器、代码分析器、搜索与索引、知识存储、可选 Agent 集成。  
> 原则：本文件是准入策略和候选评估记录，不代表候选组件已获准进入核心或已被集成。

## 1. 目标与非目标

目标：

- 以成熟开源组件补足 Radar 的非差异化基础能力，避免重复造轮子。
- 保护 Radar 的核心模型、Evidence/Asset 溯源、Pack 契约和跨模型可移植性。
- 让重型、可选、具有平台或许可证约束的能力可以单独安装、独立运行和替换。
- 对每次引入建立可复现的性能、准确率、资源占用和许可证审计记录。

非目标：

- 不以 Star 数、热度或单一榜单作为选型结论。
- 不为了组件而改变 Radar 的核心数据模型。
- 不把一个框架的内部对象直接暴露为 Radar 公共契约。
- 不在本阶段批量增加第三方依赖。

## 2. 当前仓库约束

截至本文件编写时，Radar README 声明 Python 3.9+、零依赖、可离线运行。当前 CI 同时验证 Python 3.9 和 Python 3.x。现有文档解析、Python AST 分析、JSONL Workspace Store、业务规则计算均以标准库实现。

因此，选型基线为：

1. 核心安装保持 stdlib-only，默认安装不得新增第三方 Python 包。
2. 新能力优先实现为可选 extra、独立 CLI 子进程或外部服务适配器。
3. 不允许可选依赖导入失败影响现有 CLI、离线基线和旧命令。
4. 维持 Python 3.9 兼容，除非未来通过单独版本决策明确调整最低版本；需要 Python 3.10+ 的候选只能先进入可选隔离层。
5. 组件输出必须归一化到 Radar 自己的 Asset、Evidence、Relationship、Observation 等契约，保留原始定位和来源版本。
6. 任何组件都不能自行把候选证据升级为已验证事实或需求验收通过。

## 3. 组件分层

| 层级 | 定义 | 准入要求 |
|---|---|---|
| Core | 核心数据模型、证据、规则、Workspace、CLI | 默认零第三方依赖；稳定、可离线、可迁移 |
| Optional adapter | 文档解析、代码语法、全文检索等可选能力 | 延迟导入、明确 extra/安装说明、失败可降级 |
| External tool | ScanCode、OCR、LibreOffice 等独立工具 | 子进程/协议隔离、版本探测、超时、资源限制 |
| External service | 用户自托管或云端服务 | 用户显式配置、权限最小化、数据边界清晰 |
| Pack | 行业知识、字段别名、业务规则和映射 | 数据声明，不执行任意代码，不绑定具体供应商 |

## 4. 统一准入流程

每个候选必须经过以下步骤，缺一不可：

1. **需求证明**：指出现有 Radar 能力的具体缺口、真实输入样本和失败案例。
2. **候选发现**：至少比较两个可行方案；若只有一个候选，记录原因和替代方案。
3. **许可证审查**：分别审查代码、传递依赖、模型权重、训练数据、规则库和示例数据的许可证。
4. **技术适配**：确认 Python 版本、OS/架构、离线运行、网络行为、外部二进制、模型下载及资源要求。
5. **隔离原型**：通过 Adapter 接口接入，不把供应商类型泄漏到核心模型。
6. **基准测试**：在固定样本集上比较准确率、定位完整性、吞吐、延迟、内存、磁盘和安装体积。
7. **安全审查**：检查文件解析攻击面、解压炸弹、XML 外部实体、命令注入、网络请求、临时文件和权限。
8. **决策记录**：记录 Accept / Optional / Hold / Reject，负责人、版本范围、许可证依据和复审日期。
9. **持续治理**：锁定版本和哈希，跟踪 CVE、上游维护、许可证变化和弃用通知。

## 5. 评分模型

通过硬性门槛后再评分，满分 100：

| 维度 | 权重 | 评价重点 |
|---|---:|---|
| 需求匹配度 | 20 | 是否解决已证实的 Radar 缺口 |
| 证据定位与结构保真 | 15 | 页码、段落、Sheet/Cell、行列、代码行和坐标是否保留 |
| 许可证与再分发适配 | 15 | 核心/插件/服务模式是否可合法使用和分发 |
| 技术兼容性 | 10 | Python、OS、架构、离线和私有化能力 |
| 准确率与鲁棒性 | 10 | 复杂文档、错误输入、恶意输入和边界情况 |
| 性能与资源 | 10 | 吞吐、延迟、内存、磁盘、模型体积 |
| 维护与安全 | 10 | 维护活跃度、发布节奏、漏洞响应和供应链 |
| 可替换性 | 5 | 是否能被适配器封装、是否锁定专有数据结构 |
| 运维成本 | 5 | 安装、升级、部署、排障和用户学习成本 |

建议解释：85+ 可进入接入评审；70–84 只允许可选试点；低于 70 暂缓。许可证、安全、数据主权或兼容性硬门槛失败时，不因总分高而放行。

## 6. 硬性否决与风险门槛

- 许可证不明、组件或模型权重无法确认再分发条件：Hold，不进入发布依赖。
- 强 copyleft 或商业限制可能影响 Radar 分发方式：必须经法律/项目治理确认，不得默认进入 Core。
- 需要未经用户同意上传私有代码、文档或观察值：Reject。
- 不可保留 Evidence 定位或无法区分原始文本与模型推断：不得承担正式证据提取职责。
- 解析过程可能执行文档宏、脚本或任意代码：默认禁止；必须在沙箱中验证。
- 安装或运行失败会影响旧命令、离线模式或基础 Pack 校验：Reject。
- 组件依赖模型或数据集时，模型/数据许可证必须独立审查，不能只看 Python 包许可证。

## 7. 首轮候选清单（初步判断，尚未批准接入）

| 能力 | 候选 | 初步判断 | 主要约束 / 下一步 |
|---|---|---|---|
| 全文检索 | SQLite FTS5（Python sqlite3） | 优先做无新增依赖的基线试验 | 目标环境 SQLite 是否编译启用 FTS5；中文分词与同义词需要独立评估 |
| PDF 基础文本 | pypdf | 高优先级轻量候选 | 当前最新版本的 Python 下限变化；需选择兼容 Python 3.9 的版本并测试页码、阅读顺序、扫描件边界 |
| 文档智能解析 | Docling | 高价值可选插件候选 | MIT，但要求 Python 3.10+；依赖较多，模型需下载/缓存；不得进入 Core |
| 多语言代码解析 | Tree-sitter + 各语言 grammar | 高优先级可选解析器候选 | Tree-sitter 核心 MIT；每个 grammar、binding 和生成产物需分别审查许可证；先与现有 Python AST 做差分基准 |
| PDF 高性能/布局 | PyMuPDF | 暂缓 / 法务审查 | AGPL 或商业许可路径；在许可证结论前不得作为默认依赖 |
| 许可证与 SBOM | ScanCode Toolkit | 外部工具候选 | 扫描深度较强，适合独立 CLI/服务；包、规则库、数据集和第三方依赖许可证需分别审查，资源开销需实测 |
| OCR | Tesseract / Docling OCR pipeline | 后续对比 | 语言包、二进制、模型权重和识别准确率需分别评估；必须保留页码和区域坐标 |
| 图数据库 | 暂不选型 | 先不引入 | 当前 Business Graph 是可重建投影；只有在查询规模和图算法证明现有存储不足时再评估 |

### 7.1 初步事实与官方资料

- SQLite FTS5 是 SQLite 的全文检索虚拟表模块；是否可用需在目标 Python/SQLite 构建中检测。  
  https://www.sqlite.org/fts5.html
- pypdf 支持 PDF 文本与元数据提取，许可证为 BSD-3-Clause；当前 PyPI 发布版的 Python 最低版本应以具体锁定版本元数据为准。  
  https://pypi.org/project/pypdf/
- Docling 提供 PDF、Office、HTML、图像等结构化解析，MIT；当前要求 Python 3.10+，并有模型/深度学习依赖。  
  https://github.com/docling-project/docling  
  https://github.com/docling-project/docling/blob/main/pyproject.toml
- Tree-sitter 可构建多语言具体语法树，运行时核心为 MIT；各语言 grammar 是独立项目，必须逐个审查。  
  https://github.com/tree-sitter/tree-sitter  
  https://github.com/tree-sitter/py-tree-sitter
- PyMuPDF 的上游许可说明包含 AGPL 与商业许可选项。  
  https://pymupdf.readthedocs.io/en/latest/about.html
- ScanCode 可通过 CLI 或库扫描许可证、版权和依赖；许可证和数据资产需分层核查。  
  https://scancode-toolkit.readthedocs.io/en/stable/  
  https://pypi.org/project/scancode-toolkit/

## 8. 基准测试要求

所有解析/检索组件必须使用同一套固定、可再分发或明确授权的样本集。初版样本至少覆盖：

- PDF：可搜索文本、多栏、表格、扫描件、旋转页、页眉页脚、中文字体。
- Office：DOCX 表格、页眉页脚、PPTX 备注/图表、XLSX 公式/合并单元格/隐藏 Sheet。
- 代码：Python、JavaScript/TypeScript、Java、Go；语法错误和不完整文件。
- 搜索：中英文混合、缩写、同义词、路径/符号名、精确匹配和跨文档召回。

核心指标：

- 解析成功率、字段/段落召回率、定位准确率；
- 表格单元格准确率、代码节点与关系准确率；
- Precision@K、Recall@K、MRR；
- 每千页/每千文件处理耗时、峰值内存和安装体积；
- 离线运行成功率、错误隔离率和可重复性。

任何组件的输出都必须进入 Radar 的统一 Evidence 适配层，再参与后续业务计算；不允许组件输出直接成为 Assessment 结论。

## 9. 当前阶段决策

- **批准**：继续保持 Core 零依赖；启动 FTS5 与 pypdf 的隔离基准原型。
- **可选候选**：Docling、Tree-sitter、ScanCode；先做安装隔离和真实样本评估。
- **暂缓**：PyMuPDF，待许可证审查；图数据库，待性能证据。
- **未批准**：任何候选均未进入默认依赖或正式发行包。
